# Local verification environment

Two independent, authenticated browser sessions are the only honest way to
verify collaboration. This document is how to get them on a developer machine,
against an isolated stack that can never touch a hosted project.

## What runs where

| Piece | Where it comes from | Port |
| --- | --- | --- |
| Postgres, Auth, Storage, Data API | `packages/db/supabase/config.toml` | 54321 (API), 54322 (db), 54323 (Studio), 54324 (mail) |
| Schema | `packages/db/prisma/migrations`, applied with `prisma migrate deploy` | — |
| Web app | `apps/web` | 3000 |
| Collaboration runtime | `apps/collab-nitro` (default) or `apps/collab-cloudflare` | 3001 |

Supabase CLI migrations are disabled in `config.toml` on purpose. Prisma owns
the ledger; a second source would drift.

## Bring it up

```bash
# Docker must be running.
pnpm --filter @softmaple/db db:local:start   # containers, then migrate deploy
pnpm --filter @softmaple/db db:local:status  # prints the local anon/service keys
```

`db:local:reset` drops the database and re-applies the ledger.
`db:local:stop` tears the containers down.

The script refuses to run if `DIRECT_URL` or `DATABASE_URL` name anything but
loopback, so a shell that still has hosted credentials exported cannot migrate
the wrong database.

## Configure the app

Copy the keys printed by `db:local:status` into `apps/web/.env.local`:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<anon key from db:local:status>
SUPABASE_SERVICE_ROLE_KEY=<service_role key from db:local:status>
DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres
DIRECT_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres

# Seeding. Loopback-only and opt-in; see the safety note below.
E2E_ALLOW_LOCAL_SEED=true
E2E_SEED_SECRET=<any local string>
```

None of these are secrets: the local anon and service-role keys are the
Supabase CLI's well-known development keys.

## Seeding

`POST /api/e2e/seed` with `Authorization: Bearer $E2E_SEED_SECRET` and a body of
`{"action":"seed","runId":"<8-48 chars>"}`. It creates, per run:

- three independent accounts — owner, editor and viewer — each with its own
  password, so two browsers are genuinely two people;
- a shared workspace containing all four document fixtures;
- an owner-only workspace, for the "not a member" path;
- an empty workspace the editor can also open, for empty states.

Document fixtures (`apps/web/lib/seeding/seed-fixtures.ts`):

| Fixture | Public link | Why |
| --- | --- | --- |
| `draft` | no | The everyday private case |
| `shared` | yes | Presence and shared attention are reachable |
| `mixed-language` | yes | CJK, RTL, combining marks, emoji, IME |
| `long` | no | ~145 blocks, for outline, scroll anchoring and caret stability |

Content is generated by driving a real `BlockReplica` and appending the batches
it emits through `append_document_event_batches` — the same RPC the
collaboration runtime uses. Seeded history is therefore replayable by exactly
the code path a browser exercises.

`{"action":"cleanup","runId":...}` deletes the run's users; the workspace and
document rows cascade.

### Safety

`apps/web/lib/seeding/seed-isolation.ts` admits two shapes and refuses
everything else:

- **local** — `E2E_ALLOW_LOCAL_SEED=true` *and* a loopback Supabase URL;
- **remote** — `E2E_ALLOW_REMOTE_SEED=true`, an `E2E_SUPABASE_PROJECT_REF` that
  matches the configured URL, and a ref that is not
  `SUPABASE_PRODUCTION_PROJECT_REF`.

Neither switch relaxes the other. Turning on local seeding cannot make a hosted
URL acceptable, and a mismatched remote ref cannot fall through to the local
branch. An unconfigured deployment answers 404 rather than advertising the
route.

## Feature flags

Each redesign surface has its own server-read variable, defaulting to on:

| Flag | Variable |
| --- | --- |
| `shell` | `NEXT_PUBLIC_FEATURE_SHELL` |
| `detailedPresence` | `NEXT_PUBLIC_FEATURE_DETAILED_PRESENCE` |
| `sharedAttention` | `NEXT_PUBLIC_FEATURE_SHARED_ATTENTION` |
| `fieldView` | `NEXT_PUBLIC_FEATURE_FIELD_VIEW` |

Flags are resolved once on the server and passed down as data
(`apps/web/lib/feature-flags.ts`, `components/system/feature-flags-provider.tsx`).
A flag may gate props and sibling chrome; it must never key or swap the editor
element itself, which would unmount the Lexical editor and its replica.
